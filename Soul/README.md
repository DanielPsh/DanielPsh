## 정리된 기획 (v1 MVP)

위 아이디어 노트를 기준으로 지금 단계에서 실제로 구현 가능한 범위로 좁힌 버전.

**제품**
Soul(술) — 주류 입문자를 위한 가이드. 종류별(맥주/와인/위스키/사케/막걸리/칵테일/약주/과일주)
검색·필터·상세 정보 열람, 즐겨찾기 기능을 제공하는 웹 페이지.

**범위 (v1에 포함)**
- 검색 (이름 기준) + 카테고리 필터
- 상세 정보 모달 (지역, 맛/재료, 가격, 칼로리)
- 즐겨찾기 (로그인 없이 브라우저 localStorage에 저장)

**범위 밖 (다음 단계로 미룸)**
- 이커머스 결제/입점, 광고 게재
- AI 렌즈를 통한 주류 인식
- 앱-웹 로그인 및 즐겨찾기 동기화
- 회원 DB (이메일/전번 수집)

이 항목들은 모두 인증, 결제 연동, 별도 백엔드/DB 같은 인프라가 필요해서
MVP 검증 이후 우선순위를 다시 정해서 진행한다.

**데이터 소싱**
당초 계획한 "liquor.com 정보 참고"는 그대로 가져오지 않았다. liquor.com은
테이스팅 노트·리뷰가 저작권으로 보호되는 편집 콘텐츠 사이트라, 이를 그대로
긁어 자체 DB로 쓰면 저작권/이용약관 위반 소지가 있기 때문. 대신:

| 종류 | 데이터 출처 | 비고 |
|------|------------|------|
| 칵테일 | [TheCocktailDB](https://www.thecocktaildb.com/) | 무료 공개 API, CORS 허용 |
| 맥주 | [PunkAPI](https://github.com/alxiw/punkapi) | BrewDog가 재사용 목적으로 공개한 DIY Dog 데이터의 커뮤니티 포크 |
| 와인 | [SampleAPIs Wines](https://sampleapis.com/api-list/wines) | 개발자용 공개 샘플 데이터셋 (이미지는 Vivino CDN 직링크라 미사용) |
| 위스키/사케/막걸리/약주/과일주 | 직접 작성 | 위 조건을 만족하는 오픈 데이터셋을 찾지 못함 |
| 바코드 스캔 결과 | [Open Food Facts](https://world.openfoodfacts.org/) | ODbL 라이선스, 출처 표기 조건으로 재사용 (v2.0 바코드 스캔에서 사용) |

**기술 스택**
정적 HTML/CSS/JS (원래 계획한 "HTML → 뼈대, CSS → 꾸미기, JS → 기능"을
그대로 따름). 별도 백엔드 없이 클라이언트에서 오픈 API를 직접 호출.

## Process

1. **범위 정의** — 원본 아이디어 노트의 기능을 전부 넣으면 범위가 너무 커서,
   결제/광고/AI 렌즈/앱-웹 동기화는 제외하고 검색·상세·즐겨찾기만 남긴 v1
   MVP로 좁혔다.
2. **뼈대 구현** — `main.html` / `style.css` / `script.js` / `data.js`로
   구성된 정적 페이지 작성. 로컬 서버로 직접 열어 검색, 필터, 상세 모달,
   즐겨찾기 토글을 하나씩 수동 테스트.
3. **디자인 반복** — 첫 버전(카드 그리드)이 너무 단순하다는 피드백을 받고,
   에디토리얼 매거진 스타일(세리프 헤드라인, 번호 매긴 리스트, 마스트헤드
   헤더)로 리디자인. 데스크톱/모바일 반응형 확인.
4. **데이터 소싱 재검토** — "liquor.com을 DB로 쓰자"는 요청에 대해, 편집
   콘텐츠를 그대로 복제하는 것의 저작권 리스크를 먼저 확인. liquor.com은
   카테고리 구조 참고용으로만 남기고, TheCocktailDB / PunkAPI / SampleAPIs
   같은 재사용이 명시적으로 허용된 오픈 API로 대체.
5. **API 연동** — 세 API 모두 CORS 허용 여부와 실제 응답 필드를 먼저
   확인한 뒤, 각각 우리 데이터 스키마(`id`, `name`, `type`, `region`,
   `taste`, `price`, `calories`)에 맞게 매핑하는 fetch 함수를 작성.
   API가 제공하지 않는 필드(가격, 칼로리 등)는 값을 지어내지 않고
   "정보 없음"으로 명시.
6. **출처 표기** — 각 API 이용 조건에 맞게 페이지 하단에 데이터 출처 링크
   3개를 명시.
7. **버전 관리** — 매 단계를 별도 커밋으로 분리(MVP 기본 기능 → 리디자인
   → 오픈 데이터 연동)하고, `feature/soul-mvp` 브랜치에서 PR로 병합.

## AI 렌즈 기획 (v2)

원본 노트의 "AI 렌즈 → 내가 찾고 싶은 주류의 정보"를 실제로 구현 가능한
단계로 쪼갠 계획.

**v2.0(바코드 스캔)은 구현 완료.** `scan.js`에서 네이티브
`BarcodeDetector`를 우선 쓰고, 미지원 브라우저(iOS Safari 등)는 ZXing
라이브러리로 폴백한다. 인식된 바코드는 Open Food Facts에서 조회해서
우리 DB에 같은 이름이 있으면 그 항목을, 없으면 조회 결과 자체를 상세
모달로 보여준다. 카메라 권한 거부, 제품 미검출, 조회 실패는 모두
"다시 스캔" 버튼과 함께 안내 메시지로 처리한다.

**v2.1(라벨 사진 인식)은 코드 작성·배포 완료, 진입 버튼은 대기 중.**
`Soul/worker/`의 Cloudflare Worker(Claude Vision API 호출 + Durable
Object 기반 rate limiter, SQLite 스토리지 백엔드로 무료 티어 대응)를
실제로 `https://soul-ai-lens.danielpark1030.workers.dev`에 배포했고,
`scan.js`의 `LABEL_API`도 이 실제 URL을 가리킨다. "카메라로 프레임
촬영 → Worker 호출 → `LIQUORS`에서 퍼지 매칭 → 매칭 실패 시 이름 외
전부 '정보 없음'으로 채우는" 흐름도 fetch/캡처 모킹으로 로직 전부
확인했다.

다만 실제로 눌러보면 아직 실패한다 — Anthropic 계정에 결제 수단이
등록되지 않아 API 호출 자체가 거부된다("credit balance too low").
매번 실패하는 버튼을 그대로 노출하는 건 나쁜 경험이라, `main.html`의
"라벨로 찾기 (베타)" 버튼은 `hidden` 처리해서 화면에서 숨겨뒀다.
[console.anthropic.com/settings/billing](https://console.anthropic.com/settings/billing)에서
크레딧을 충전한 뒤 `main.html`에서 그 버튼의 `hidden` 속성만 지우면
바로 켜진다. 그때까지는 v2.0(바코드 스캔)이 AI 렌즈의 기본 동작
방식이다.

### 목표
카메라로 술병을 비추면 어떤 술인지 찾아준다.

### 접근 방식 후보

1. **바코드 스캔 (권장, 1단계)** — 브라우저 카메라로 바코드를 읽어
   [Open Food Facts](https://openfoodfacts.github.io/openfoodfacts-server/api/)의
   `GET /api/v2/product/{barcode}.json`으로 실제 제품 정보를 조회한다.
   (barcode 단건 조회는 확인 완료 — 검색 엔드포인트는 봇 차단으로 막혀
   있었지만 단건 조회는 정상 응답한다.) 바코드는 고유 식별자라 정확도가
   사실상 100%이고, 별도 ML/서버 없이 지금 아키텍처 그대로 구현 가능하다.
   단점은 "라벨을 보고 인식한다"는 AI 렌즈의 컨셉과는 거리가 있고, 바코드가
   없거나 훼손된 병은 인식하지 못한다는 것.

2. **라벨 사진 인식 (2단계, 이름값에 맞는 진짜 AI 렌즈)** — 사용자가 찍은
   라벨 사진을 비전 지원 LLM에 보내 브랜드/제품명을 추출하고, 그 결과를
   우리 데이터(직접 작성분 + API 소싱분)에서 퍼지 매칭한다. 조명·각도에
   따라 정확도가 흔들리고, 결정적으로 **아키텍처가 바뀐다**: 지금 Soul은
   백엔드가 없는 순수 정적 사이트인데, 비전 API 키를 프론트엔드 JS에 그대로
   넣으면 브라우저 개발자 도구에서 그대로 노출돼 누구나 우리 API 크레딧을
   가져다 쓸 수 있다. 즉 이 단계로 가려면 키를 숨겨줄 최소한의 서버(서버리스
   함수 하나라도)가 처음으로 필요해진다.

### 추천 순서
- **v2.0**: 바코드 스캔 + Open Food Facts. 지금의 "정적 프론트엔드" 전제를
  깨지 않고 구현 가능하니 먼저 진행.
- **v2.1**: 라벨 인식이 정말 필요해지면, 그때 서버리스 함수를 하나 추가해
  키를 감추는 구조로 확장한다. v2.0에서 만든 "카메라 → 인식 → DB 조회 →
  상세 모달" 파이프라인과 UI는 그대로 재사용한다.

### 단계별 구현 계획 (v2.0)
1. 카메라 권한 요청 + 실시간 비디오 스트림 UI (`getUserMedia`)
2. 브라우저 `BarcodeDetector` 지원 여부를 확인하고 없으면 zxing-js 등
   WebAssembly 기반 라이브러리로 폴백 — **iOS Safari는 2026년 현재도
   `BarcodeDetector`를 지원하지 않으므로 폴백은 선택이 아니라 필수.**
3. 인식된 바코드로 Open Food Facts 조회 → 우리 데이터 스키마로 매핑
4. 우리 DB(큐레이션+API 소싱)에 같은 제품이 이미 있으면 그 항목의 상세
   모달을 열고, 없으면 Open Food Facts 응답만으로 임시 상세 화면을 보여준다
5. 실패 상태 UI (바코드 미검출, 카메라 권한 거부, 조회 결과 없음)

### v2.1 구체적 실행 계획 (라벨 사진 인식, 미착수)

v2.0에서 이미 카메라 UI(`scan.js`)와 "인식 결과 → DB 매칭 → 상세 모달"
파이프라인을 만들어뒀으니, v2.1은 "바코드 대신 사진을 인식 서버로 보낸다"는
부분만 새로 얹으면 된다.

**아키텍처**
Soul은 지금 백엔드가 전혀 없는 정적 사이트라, 비전 LLM API 키를 안전하게
보관할 곳이 없다. 서버리스 함수를 하나 추가해야 하는데, Cloudflare
Workers를 추천한다 — 무료 티어가 하루 10만 요청까지 무료이고, 별도
프레임워크 없이 함수 하나만 배포하면 되어 지금 프로젝트 규모에 맞다.
(Vercel/Netlify Functions도 대안이 될 수 있으나, 이미 GitHub 저장소
기반이라 Cloudflare Workers 쪽이 배포 설정이 가장 가볍다.)

**요청 흐름**
1. 프론트(`scan.js` 재사용) — 카메라 프레임을 캔버스로 캡처해 base64
   JPEG로 인코딩
2. 프론트 → Cloudflare Worker로 POST (이미지 base64만 전송, 다른 개인
   정보 없음)
3. Worker → 비전 지원 LLM에 "이 술병 라벨에서 브랜드명과 제품명만
   추출해줘, 모르면 unknown" 프롬프트로 이미지 전달 (API 키는 Worker의
   비밀 환경변수로 보관, 클라이언트에는 절대 내려가지 않음)
4. Worker → 인식 결과(JSON: 브랜드/제품명)를 프론트로 반환, 이미지 자체는
   응답 후 즉시 폐기(로그에도 남기지 않음)
5. 프론트 — 반환된 이름으로 `LIQUORS` 배열에서 퍼지 매칭 → 있으면 해당
   항목 모달, 없으면 "인식된 이름: OOO (DB에 없음)" 안내. 이때도 v2.0의
   실수(도수를 칼로리 라벨에 표시)를 반복하지 않도록, 매칭 실패 시
   모달의 지역/맛/가격/칼로리는 전부 "정보 없음"으로 채우고 인식된
   이름만 표시한다 — 비전 LLM이 억지로 값을 채워 답하더라도 우리 쪽에서
   신뢰하지 않는다.

**남용 방지 (rate limiting)**
Worker 엔드포인트에 키 없이 누구나 호출 가능하므로, 요청 남용 시 비전
API 비용이 그대로 새어나간다. 이때 Cloudflare KV로 카운터를 만드는 건
피해야 한다 — 무료 티어 KV 쓰기가 하루 1,000회뿐이라 요청마다 카운터를
쓰면 KV 쓰기 한도가 실제 요청 한도(10만/일)보다 먼저 바닥난다. 대신
Durable Objects(SQLite 스토리지 백엔드는 2025년부터 무료 티어에도
포함됨)로 IP별 카운터를 두고 분당/일당 호출 수를 제한한다. 단, Durable
Object 호출이 Worker의 하루 10만 요청 한도와 별개로 집계되는지는 공식
문서에서 명확히 확인하지 못했으니, 실제 구현 시 Cloudflare 문서에서
정확한 과금/한도 방식을 재확인해야 한다.

**개인정보 안내**
사용자가 찍은 사진이 외부(Cloudflare Worker → 비전 LLM)로 전송된다는
점을 스캔 UI에 짧게 안내한다("사진은 인식에만 쓰이고 저장되지 않아요").

**구현 순서**
1. Cloudflare Workers 계정 생성 + `wrangler` CLI로 로컬 개발 환경 구성
2. 비전 LLM 호출을 Worker 안에서 먼저 curl/스크립트로 검증 (라벨 사진
   샘플로 브랜드명 추출이 실제로 되는지)
3. Durable Object 기반 rate limiter 추가
